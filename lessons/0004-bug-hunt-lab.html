Lesson 4 — Guided bug hunt: what can be fixed in this repo

⏱ 30–45 min Skill: spot → prove → fix → justify Prereq: Lesson 2

How this works: this is a guide, not an answer key. Each station gives you a place to look and a way to prove your suspicion. Form your own opinion before opening the hints — on Friday, the justification matters more than the fix. Hints escalate: what class of issue → how to prove it → fix sketch + the one-line interview justification.

First: the triage frame (this is what gets scored)

Every suspicious thing you find lands in one of three buckets. Practice saying the bucket out loud:

  1. Definite bug — fix it, say why: "any user can delete anyone's habit; the guard is one line."
  2. Judgment call — discuss the trade-off: "cross-user search looks intentional — the UI prints owner #N — but it leaks user ids; I'd confirm with the team."
  3. Looks deliberate — leave it, mention it: "this sleep has a comment claiming a rate limit; I'd flag the latency cost rather than rip it out silently."

Mislabeling bucket 2 as a bug (or ignoring a bucket-1 bug because it's subtle) is the actual failure mode. Now the stations.

Tier 1 — the five most likely assessment tasks

Station 1 — The check-in trio backend/app/routers/habits.py:133–154

Look first: between line 139 and 150, what does the code verify about who owns this habit? Then look at line 152: where does the returned streak number come from, and what does analytics.py compute it from instead? And line 153 — what does that sleep cost on every check-in?

Prove it: pick a habit id that is not yours (search results show owner #N), then
Invoke-RestMethod -Method Post -Uri "http://localhost:8000/api/habits/<their-id>/checkin" -Headers @{Authorization="Bearer 1"}
Success = you just wrote a log to someone else's habit. Then restart the backend (Run.ps1) and check in again — compare the returned streak with what GET /api/habits/<id>/stats says.

Hint 1 · what class of issue

Three separate issues share one endpoint: a missing authorization check (bucket 1), state derived from an in-process dict instead of the database (bucket 1 — it resets on restart and ignores deleted logs), and an artificial latency on the hottest write path (bucket 2 — the comment is plausible, the placement is not).

Hint 2 · proof & blast radius

After a restart the cache is empty, so the first check-in reports streak: 1 while /stats (which recomputes from real logs) reports the true value — two endpoints, two different truths, same data. The sleep blocks a threadpool worker per request; under load that's your throughput ceiling.

Hint 3 · fix sketch

Add the ownership guard (see Station 3's one-liner). Replace the cache read with the real calculation (current_streak on the habit's log dates) or drop the cache entirely — the honest fix is to return what the DB proves. For the sleep: move it out of the request path (background task / queue) or make it conditional, and say the trade-off: "I kept the rate-limit intent but stopped taxing every user for it."

Station 2 — The streak that lies about today backend/app/analytics.py:4–10

Look first: day = date.today(), then while day in dates. What happens when the user did everything right yesterday but hasn't checked in yet today — is the streak really zero?

Prove it: find any habit whose dashboard card does not show "Done ✓" but whose history shows an unbroken chain up to yesterday. Its card will read "🔥 0 day streak".

Hint 1 · what class of issue

Logic bug, and a subtle one: the function conflates "checked in today" with "streak alive". Most habit apps grant grace until the day ends — this one doesn't.

Hint 2 · proof & blast radius

current_streak has 4 callers across habits.py and stats.py — fixing it in one place fixes the card, the detail page, and the dashboard at once. That's a nice blast-radius observation to say out loud.

Hint 3 · fix sketch

Anchor the walk at yesterday when today isn't logged: day = date.today() if date.today() in dates else date.today() - timedelta(days=1), then walk back. Justification: "a streak shouldn't hit zero at midnight; apps grant the current day as grace."

Station 3 — The IDOR family: delete, logs, stats, cheer backend/app/routers/habits.py:117–130, 157–168, 171–191, 194–219

Look first: each of these does db.get(Habit, habit_id) and then… what check is missing before touching data? Compare with create_habit, which correctly stamps user_id=user.id.

Prove it (destructive — on the demo DB only):
Invoke-RestMethod -Method Delete -Uri "http://localhost:8000/api/habits/<their-id>" -Headers @{Authorization="Bearer 1"} → {"ok":true}. Reading someone's /logs or /stats with your token proves the same class without destroying data — prefer that in a live interview.

Hint 1 · what class of issue

Broken access control (IDOR) — authenticate-but-not-authorize. One missing line, four-plus endpoints. Reading logs of another user is a data leak; deleting is worse.

Hint 2 · proof & blast radius

The frontend never triggers it (it only shows your own habits), which is why it survives demoing — that's a great sentence: "the UI hides it, the API doesn't."

Hint 3 · fix sketch

One guard, repeated or extracted: after fetching, if habit.user_id != user.id: raise HTTPException(404, "Habit not found") — 404, not 403, so you don't confirm existence to strangers. Mention extracting it into a shared dependency or helper to show DRY thinking.

Station 4 — Login: plaintext passwords, token = user id backend/app/routers/auth_routes.py:16–24

Look first: line 19 compares the password how? Line 22 returns what as the token? Then open deps.py: what does it do with that number?

Prove it: Invoke-RestMethod -Uri http://localhost:8000/api/habits -Headers @{Authorization="Bearer 2"} — you are user2 now. No login, no secret, just arithmetic.

Hint 1 · what class of issue

Two for one: credentials stored/compared in plaintext (the model field is even named hashed_password), and an unguessable-but-guessable token — the token is the primary key. Both are bucket-1.

Hint 2 · proof & blast radius

Every protected endpoint trusts this token, so the fix's blast radius is "everything" — which is also why it's a great interview topic: small change, systemic meaning.

Hint 3 · fix sketch

Hash on create with bcrypt/passlib, verify with verify(); issue an opaque random token (or a signed JWT with expiry) stored server-side. Justification: "auth depends on tokens being unguessable; sequential ints are effectively usernames."

Station 5 — SQL injection in search backend/app/routers/habits.py:26–41

Look first: line 32–37: the query is an f-string inside text(). Where does {q} end up?

Prove it:
Invoke-RestMethod -Uri 'http://localhost:8000/api/habits/search?q=a%27%20OR%201%3D1--' -Headers @{Authorization="Bearer 1"}
The ' closes the literal, OR 1=1 makes the WHERE always true, -- comments out the rest — you get every habit from every user.

Hint 1 · what class of issue

Classic SQL injection — bucket 1, textbook. Also note the result leaks user_id for all users (ties back to the bucket-2 search discussion).

Hint 2 · proof & blast radius

This is the only place in the repo that builds SQL by string — everything else uses the ORM. Saying that ("it's the one outlier") shows you read the whole codebase.

Hint 3 · fix sketch

Bind parameters: text("... WHERE name ILIKE :q ...") with q=f"%{search}%" passed as a bound value — or just use the ORM: db.query(Habit).filter(Habit.name.ilike(f"%{q}%")). Justification: "user input never becomes SQL text; the ORM/binding does the escaping."

Tier 2 — performance & consistency (say these, fix only if asked)

Station 6 — The dashboard that reads 60k rows per call backend/app/routers/stats.py:15–82

Look first: lines 29–34 load all log rows for the user into Python. Lines 23–28: which habits are included — compare with list_habits's archived.is_(False) filter. Line 17/21: what does the user_id query param allow?

Hint 1 · what class of issue

Performance (full-table read for aggregates), a consistency bug (archived habits count toward totals here but are hidden in the list — the two endpoints disagree), and the same user_id IDOR as Station 7.

Hint 3 · fix sketch

Aggregate in SQL (GROUP BY date for the heatmap, window functions or grouped queries for streaks), filter archived consistently, drop or guard the user_id param. Justification: "the dashboard is the most-polled endpoint; it should return aggregates, not rows."

Station 7 — N+1 in the habit list backend/app/routers/habits.py:44–83

Look first: the loop at lines 59–70 issues how many queries per habit? With N habits, how many round-trips?

Hint 1 · what class of issue

N+1 queries — two extra per habit. Also: the user_id param (line 50) lets any caller list anyone's habits — same family as Station 6.

Hint 3 · fix sketch

One grouped query for totals (GROUP BY habit_id) and one for today's logs, then stitch in Python. Justification: "constant number of queries regardless of habit count."

Station 8 — The frontend that polls forever frontend/src/components/Dashboard.jsx:12–33

Look first: line 31 sets an interval — how often? And inside refresh, the loop at 20–23 awaits each stats call sequentially. Multiply that by the interval and by Station 6's row count.

Hint 1 · what class of issue

Frontend amplification: a 4-second full refresh (dashboard + list + N stats calls, each heavy) — the backend issues compound. Open devtools → Network and watch the wall of requests.

Hint 3 · fix sketch

Poll slower or on focus/visibility, parallelize with Promise.all, or push one aggregate endpoint that replaces N stats calls. Justification: "fix the amplification before micro-optimizing each call."

The 60-minute drill (do this once before Friday)

  1. Pick one Tier-1 station (Station 1 or 2 are the most likely to be the actual task).
  2. Write a 5-line spec in .scratch/<feature>/spec.md (repo convention — free process points).
  3. Fix it. Add the missing guard / correct the anchor / bind the parameter — smallest correct change.
  4. Prove it with the PowerShell pair from Lesson 1 §4 (before AND after).
  5. Say the justification out loud, in one sentence, twice: what was wrong, why your fix is the right size.
